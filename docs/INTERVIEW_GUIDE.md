# 面试讲解指南

## 一分钟版本

这个项目解决的是“如何把 GA4 嵌套埋点从一次性查询沉淀成可治理经营数据资产”。我从 Google 官方 BigQuery 样例提取 92 天、4,295,584 条事件和 3,982,732 条商品明细，用 DuckDB 建设 ODS、DWD、DWS、ADS 四层模型，统一用户、会话、订单、收入、有序漏斗与留存口径；再用 19 条质量规则、FastAPI、ECharts 看板和 Parquet 契约完成交付。正式运行得到 270,154 位用户、360,129 个会话、4,452 个订单和 1.35% 会话转化率。

## 项目背景与业务价值

GA4 原始导出适合保留完整事件，但嵌套参数、重复事件和口径差异使业务同学难以稳定复用。项目价值不是“做一张图”，而是把解析、指标、质量、分析和交付连成证据可追溯的流水线，让经营看板和通用指标平台可以重复消费同一份标准结果。

## 系统架构与数据流

1. BigQuery 通过 `_TABLE_SUFFIX` 限定 20201101—20210131。
2. 事件 SQL 用相关子查询提取 `event_params`；商品 SQL 单独 `UNNEST(items)`，避免笛卡尔积。
3. Arrow batch 流式写入 Parquet，避免 4.3M 行一次性进入 pandas 内存。
4. DuckDB 建 ODS 原始层、DWD 明细层、DWS 会话主题、ADS 指标应用层。
5. FastAPI 提供统一查询接口，ECharts 渲染 KPI、趋势、漏斗、留存、渠道、商品与异常。
6. 标准 Parquet 输出供 `growth-intel-platform` 继续接入，两个仓库仍可独立运行。

## 指标口径怎么讲

- 用户：匿名 `user_pseudo_id` 去重；明确它不是跨设备会员。
- 会话：用户 ID 与 `ga_session_id` 拼接，防止单独使用后发生跨用户碰撞。
- 订单：purchase 中非空 transaction_id 去重；23 条缺失 ID 的 purchase 保留为质量警告，不虚构补号。
- 漏斗：比较同一用户各步骤首次发生时间，并要求时间单调递增，而不是把五个独立 UV 直接相除。
- 留存：首次活跃周为 cohort；W1 加权留存为各可观察 cohort 的留存人数合计 / cohort 人数合计。
- 渠道：使用 `traffic_source` 的首次获取口径，不宣称是会话 last-click。

## 复杂 SQL 与窗口函数

BigQuery 的难点是嵌套结构和扫描控制。`event_params` 使用键值相关子查询取 `ga_session_id`、`page_location`，商品在独立查询展开。DuckDB 用 `row_number()` 做组合键去重，用带 FILTER 的 `min(event_timestamp)` 建有序漏斗，用 `first_value()` 计算 cohort 基数，用 `ntile(5)` 构造 RFM 分数，并用 7 日窗口均值/标准差识别异常。

## 数据质量

19 条规则分 critical 与 warning。17 条正式通过、0 条失败；23 条缺失订单号和 448 条 purchase 商品数量异常被标成 warning。这样既不掩盖官方混淆数据的不一致，也不把已知源限制误报为流水线失败。测试 fixture 的新鲜度规则标为 N/A，因为它只覆盖 5 个边界日期。

## 技术选择

- BigQuery：直接读取官方源并利用分区后缀裁剪。
- Parquet + Arrow：列式压缩、跨项目契约、流式降低峰值内存。
- DuckDB：本地可复现复杂 SQL，适合作品集和分析交付。
- FastAPI + ECharts：接口和展示解耦，前端不拼任意 SQL。
- pytest + ESLint + Vite + GitHub Actions：验证数据、API、SQL边界和前端构建。

## 遇到的问题与解决

电脑可用内存不足以一次性加载完整事件表，因此没有缩小数据冒充全量，而是把提取改成单流 Arrow batch + ParquetWriter。Google 下载通道还出现过一次临时 503；脚本保持查询缓存与文件覆盖安全，重试后完整落地。测试最初会把 fixture 平台文件写到正式目录，后来隔离为 `data/platform_fixture/`，避免 CI 污染真实契约。

## 性能与增量

正式查询预检约 2.42 GB，远低于每条 20 GB 上限。生产增量可按 `_TABLE_SUFFIX` 读取新增和回补日，在 DWD 以事件时间、事件名、用户和订单组合键幂等覆盖；日 KPI 只重算受影响日期，留存则重算与这些日期相关的 cohort。大规模生产场景可把 ADS 留在 BigQuery 并使用分区、聚簇和调度。

## 项目限制

数据是混淆样例，不代表当前经营；用户和归因均受 GA4 口径限制；异常是统计提示而非因果结论；本地 DuckDB 没有企业调度和权限体系。面试中主动说明这些限制，比夸大业务提升更可信。

## 高频追问与推荐回答

1. **为什么不能同时 UNNEST event_params 和 items？** 两个重复字段同时展开会把每个参数与每个商品组合，产生笛卡尔积并放大收入；所以分两条 SQL，通过事件时间、用户和交易号在分析层关联。
2. **为什么漏斗购买人数 2,635 小于购买用户 4,419？** 购买用户只要求出现 purchase；顺序漏斗还要求此前四步完整且首次时间依次递增，两者口径不同。
3. **为什么订单不是 purchase 行数？** 同一 transaction_id 可能重复出现或跨日重现，订单采用全周期非空 transaction_id 去重。
4. **质量 warning 为什么不直接清洗？** 缺失订单号无法可靠推断，强行补值会制造数据；保留异常并把指标排除规则写清楚更可审计。
5. **GA4 UI 为什么可能与 BigQuery 不一致？** UI 可能使用不同身份空间、归因模型、时区、数据建模和阈值，本项目明确以公开导出表口径为准。
6. **这个项目怎样接入通用平台？** `data/platform` 输出事件、商品、日 KPI、漏斗、渠道和用户价值 Parquet，配合 YAML 字段语义与指标配置导入；GA4 仓库仍能独立运行。
7. **分析结论能否指导真实运营？** 方法和口径可以迁移，但样例结论本身不能；真实业务需要换成企业数据、补充活动日历、实验和会话级归因后再决策。
